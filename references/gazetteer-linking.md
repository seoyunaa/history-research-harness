# 게이지티어 연결 참조문서

`places.csv`·`corpus/gazetteer-master.csv`의 게이지티어 ID 열(`whg_id` 등)을 채우는 절차. 목적은 프로젝트의 지명 테이블을 외부 역사 게이지티어의 안정 식별자(stable ID)에 연결하여 링크드 데이터(LOD) 상호운용을 가능케 하는 것이다. **본 문서는 절차만 규정한다. 실제 매칭 값은 아래 게이트를 통과한 뒤 저자가 직접 기입한다.**

## 0. 원칙

- **자동 매칭 단정 금지.** 검색·조회 결과는 후보(candidate)일 뿐이며, 어떤 도구·API·이 문서의 절차도 매칭을 확정하지 못한다.
- **저자 검증 게이트(human gate).** 모든 게이지티어 ID 기입은 저자가 후보를 검토·승인한 뒤에만 이루어진다. 미검증 후보는 CSV 본 열에 넣지 않는다.
- **근거 기록 의무.** 승인된 매칭은 근거(좌표 일치, 시대, 이표기, 출처)를 함께 남긴다.
- **지어내지 않는다.** 식별자·좌표를 추정으로 채우지 않는다. 불확실하면 비워 두고 상태를 `unmatched`로 표기한다. 좌표가 없으면 `[GAP:좌표]`.

## 1. 대상 자원

어떤 게이지티어를 쓸지는 `research-profile.md` §5에 적는다. 후보 자원과 성격은 `references/connectors.md`(예시 목록).

- **범용**: World Historical Gazetteer(WHG) — 시대·언어를 가로질러 지명을 연결하는 통합 게이지티어. → `whg_id`.
- **분야별(예시)**: 고대 지중해권이면 Pleiades, 중국사면 CHGIS 같은 분야 게이지티어. 마스터의 `chgis_id` 열은 중국사용 예시 열이다 — 다른 분야면 비워 두거나, 저자가 분야 게이지티어 ID 열(예: `pleiades_id`)을 추가한다(열 추가는 `corpus/_relational-schema.md`·verify.py와의 정합을 함께 확인).
- **보조 검증용**: 시대·지역이 한정된 게이지티어나 노선 데이터는 좌표·노선 교차검증에만 쓰고, 마스터 ID 열에 자동 기입하지 않는다.

## 2. 열 정의

`places.csv`·마스터에 다음 열을 둔다.

| 열 | 의미 |
|---|---|
| `whg_id` | WHG place 식별자(승인된 경우에만). 형식 예: WHG 내부 place id 또는 정본 URI. |
| `{분야 게이지티어}_id` | 분야 게이지티어 식별자(승인된 경우에만). 예: `chgis_id`, `pleiades_id`. |
| `match_status` | `unmatched` / `candidate` / `verified` 중 하나. |
| `match_basis` | 승인 근거 요약(좌표 일치도, 시대, 이표기, 참조 출처). |
| `match_date` | 저자 검증일. |

미검증 상태에서 ID 열은 비워 둔다. 외부 DB의 원천 정보(원 ID·위치 비정 근거·설명 URI)를 잃지 않으려면 `corpus/_places-template.md`의 확장 열(`source_db`·`source_id` 등)을 쓴다.

## 3. 절차

공개본에는 게이지티어 조회 전용 도구가 들어 있지 않다. 각 게이지티어의 웹 화면이나 공개 API로 조회하고, 결과를 아래 작업표에 손으로(또는 직접 만든 스크립트로) 모은다. 스크립트를 쓰면 입력·명령·출력을 매니페스트에 남긴다.

### 3.1 조회 (후보 수집)

1. `places.csv`에서 미매칭 행을 추출한다(`match_status`가 `unmatched`).
2. **게이지티어 조회:** 지명(현대명·역사명·이표기)과 대략 좌표로 검색한다. 각 후보의 ID, 표시 명칭, 좌표, 유효 시대, 출처를 기록한다. API 토큰이 필요한 서비스는 토큰을 환경변수로 넘기고 저장소에 기록하지 않는다.
3. **시대 한정 게이지티어:** 레코드마다 유효기간이 있는 게이지티어(같은 지명이 시대별로 여러 레코드)는 연구 시대 창으로 거른다.
4. **후보 검토표:** 여러 조회 결과를 바로 마스터에 합치지 말고, 먼저 `_workspace/{논문}/gazetteer_review.csv` 같은 작업표에 모은다. 각 행에 출처 게이지티어, 후보 ID, 좌표, 기존 마스터 항목과의 거리(있으면), 비고를 둔다.
5. 이 단계에서 모든 행의 `match_status`(또는 `review_status`)는 `candidate`다. **CSV의 ID 열은 아직 비어 있다.**
6. **승급 제안:** 저자 검토 뒤 승인 행만 `verified`(또는 `approved`)로 바꾸고, 마스터에 반영할 내용(새 행 추가 / 기존 행 ID 채우기)을 별도 제안 목록으로 정리한 뒤 저자가 마스터를 고친다. 도구나 모델이 마스터를 직접 고치지 않는다.

### 3.2 저자 검증 게이트

저자는 각 후보에 대해 다음을 확인한다.

- **좌표 일치:** 프로젝트 좌표와 게이지티어 좌표의 거리(허용 오차를 명시). 좌표를 다른 전거로 재정박한 이력이 있으면 감안한다.
- **시대 적합:** 연구 시대와 게이지티어 레코드의 유효기간이 겹치는가.
- **동명이지(同名異地) 배제:** 같은 이름의 다른 장소가 아닌지.
- **이표기 정합:** 역사 명칭·음역 변이가 후보의 명칭 변이 목록과 부합하는가.

판정:
- 승인 → `match_status=verified`, 해당 ID 기입 제안 생성, `match_basis`·`match_date` 작성.
- 보류/기각 → ID 열은 비운 채로, `match_status`를 `unmatched`로 되돌리거나 근거 메모만 남긴다.

### 3.3 근거 기록

승인 행마다 `match_basis`에 최소한 다음을 담는다: 좌표 일치도(예: Δ<2km), 시대 근거, 대조에 쓴 이표기, 인용 출처(게이지티어 레코드 URL 또는 ID). 보조 자원으로 교차확인했다면 그 사실도 적는다.

## 4. LOD 상호운용 목적

게이지티어 ID는 프로젝트 지명을 외부 게이지티어에 링크드 데이터로 접합하기 위한 것이다. 검증된 식별자가 채워지면 프로젝트 테이블을 통합 게이지티어에 기여·정렬할 수 있고, 분야 게이지티어를 통해 해당 시대의 행정지리에 정박할 수 있다. 이로써 서로 다른 시대·언어·표기의 지명 레코드가 공통 식별자로 상호참조된다. Pelagios 계열의 게이지티어 링크드 데이터 모델과 같은 방향의 상호운용을 지향한다.

## 5. 하지 않는 것

- 자동 스크립트로 ID를 일괄 확정하지 않는다(후보 수집까지만 자동화 허용).
- 좌표·식별자를 추정으로 채우지 않는다.
- 보조 자원의 노선/좌표를 ID 열에 기입하지 않는다.
- 게이지티어의 현대 좌표를 사료 시대의 위치로 단정하지 않는다(하도·해안선·도시 위치는 바뀐다).
